# ADR-0002. Вибір стратегії баз даних та збереження даних

## Статус
Accepted

## Контекст (Context)
Предметна область університетського порталу оперує суворо структурованими даними зі складними реляційними зв'язками (факультети → кафедри → групи → студенти → дисципліни → оцінки → відомості). Для електронного журналу критичною є транзакційна цілісність (ACID) та незмінність історії змін (`NFR-06`, `QAS-3`). Водночас модуль онлайн-тестування (`Assessment`) під час модульних тижнів генерує тисячі частих запитів на автозбереження проміжних відповідей студентів (`NFR-02`, `QAS-1`), а розклад занять має високе співвідношення читання до запису (`Read-Heavy`, `NFR-01`).

## Рішення (Decision)
Прийнято рішення використовувати гібридний підхід збереження даних (**PostgreSQL + Redis**):
1. **Основне сховище (System of Record) — PostgreSQL 16+:**
   * Використовується для всіх доменних модулів із логічним розділенням за схемами (`schema_schedule`, `schema_gradebook`, `schema_requests`, `schema_assessment`, `schema_audit`).
   * Забезпечує повну ACID-сумісність для виставлення оцінок, формування відомостей і ведення `append-only` таблиць журналу аудиту.
   * Тип даних `JSONB` використовується для гнучкого зберігання конструкторів запитань у тестах та динамічних полів шаблонів студентських заяв без втрати можливості індексації.
2. **Кеш та буфер оперативних даних — Redis 7+:**
   * Використовується для кешування розкладу занять (`TTL = 15 хв` з інвалідацією при зміні) для досягнення `Latency p95 ≤ 150 ms` (`NFR-01`).
   * Використовується як швидкий персистентний буфер (з увімкненим AOF — Append-Only File) для автозбереження проміжних відповідей студентів під час проходження онлайн-тестування кожні 10 секунд (`NFR-04`, `QAS-1`) із подальшим фінальним збереженням результату в PostgreSQL.

## Розглянуті альтернативи (Alternatives Considered)
* **Документо-орієнтована СУБД (MongoDB):**
  * *Переваги:* Зручне зберігання варіантів тестів та анкет заяв у вигляді документів без жорсткої схеми.
  * *Недоліки:* Складність реалізації складних аналітичних вибірок для деканату (зведені відомості успішності по курсах і групах), вищі накладні витрати на багатодокументні транзакції порівняно з PostgreSQL, який вже підтримує `JSONB`. Відхилено.
* **Виключно PostgreSQL без рівня кешування (Single Database):**
  * *Переваги:* Простіша інфраструктура (на один компонент менше в Docker Compose).
  * *Недоліки:* Під час пікового навантаження 2 500 RPS на автозбереження відповідей тестів (`QAS-1`) часті операції `UPDATE` створять високе навантаження на дискову підсистему (IOPS) та блокування рядків, що погіршить час відповіді електронного журналу та розкладу. Відхилено.

## Наслідки (Consequences)
* **Позитивні наслідки:**
  * Гарантована цілісність академічних даних, зовнішніх ключів та транзакцій (ACID) у PostgreSQL.
  * Розвантаження основної БД від інтенсивного запису чернеток тестування та частих запитів на читання розкладу завдяки Redis (`QAS-1`, `QAS-5`).
  * Збереження прогресу тестування при перезапуску контейнерів бекенду (`RPO = 0` у `QAS-2`).
* **Негативні наслідки / Компроміси (Trade-offs):**
  * Необхідність реалізації механізму інвалідації кешу розкладу при внесенні коректив диспетчером деканату (ризик короткочасної неузгодженості даних до моменту очищення кешу).
  * Додатковий компонент (Redis) у контурі розгортання, моніторингу та резервного копіювання.
