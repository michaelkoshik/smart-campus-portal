# ADR-0003. Вибір стратегії автентифікації та безпеки

## Статус
Accepted

## Контекст (Context)
Університетський портал обробляє персональні дані студентів і викладачів та керує критичними академічними показниками (оцінками заліків та іспитів). Згідно з вимогами фахівця із захисту інформації (`Security Officer`), специфікацією безпеки (`NFR-05`, `NFR-06`) та сценарієм `QAS-3`, система повинна забезпечувати надійну автентифікацію, гранульоване розмежування доступу, підтримку горизонтального масштабування без прив'язки до стану сервера (`stateless`, `NFR-08`) та можливість інтеграції з корпоративним обліковим записом університету (SSO).

## Рішення (Decision)
Прийнято рішення впровадити стандартизований стек автентифікації та авторизації на базі **OAuth 2.0 / OpenID Connect (OIDC)** з використанням **Keycloak** (або сумісного Identity Provider) та токенів **JWT (RS256)**:
1. **Автентифікація (OIDC + JWT):**
   * Використовується потік `Authorization Code Flow with PKCE` для вебклієнта.
   * Короткоживучий `Access Token` (JWT, підписаний асиметричним ключем `RS256`, `TTL = 15 хв`) передається у заголовку `Authorization: Bearer` і валідується бекендом локально без звернення до БД на кожен запит.
   * Довгоживучий `Refresh Token` (`TTL = 7 днів`) зберігається у захищеному `HttpOnly; Secure; SameSite=Strict` cookie з механізмом ротації (Refresh Token Rotation).
2. **Авторизація (Гібридна модель RBAC + ABAC):**
   * **RBAC (Role-Based Access Control):** базові ролі системи (`STUDENT`, `TEACHER`, `DEAN_STAFF`, `ADMIN`).
   * **ABAC (Attribute-Based Access Control):** перевірка контекстних атрибутів на рівні бізнес-логіки (наприклад, викладач має право змінювати оцінки лише в межах закріпленої за ним дисципліни та академічної групи; студент бачить лише власні оцінки та заяви).
3. **Захист даних та аудит:**
   * Весь зовнішній та внутрішній трафік захищено протоколом **TLS 1.3**.
   * Чутливі персональні поля (РНОКПП, серія/номер паспорта) шифруються на рівні застосунку алгоритмом **AES-256-GCM** перед записом у БД.

## Розглянуті альтернативи (Alternatives Considered)
* **Класичні серверні сесії з Cookies (Stateful Session Auth):**
  * *Переваги:* Просте миттєве відкликання сесії користувача на сервері.
  * *Недоліки:* Потребує централізованого сховища сесій для всіх реплік при масштабуванні (`QAS-5`), ускладнює подальшу інтеграцію мобільного застосунку та єдиного входу (SSO) між іншими сервісами університету (бібліотека, Wi-Fi, корпоративна пошта). Відхилено.
* **Власна реалізація JWT-автентифікації без OIDC-провайдера (Custom Auth Service):**
  * *Переваги:* Менше компонентів інфраструктури на старті.
  * *Недоліки:* Високий ризик помилок безпеки при самостійній реалізації відновлення паролів, двофакторної автентифікації (2FA) та блокування брутфорс-атак; відсутність стандартного SSO для інтеграції з університетським каталогом користувачів (LDAP / Active Directory). Відхилено.

## Наслідки (Consequences)
* **Позитивні наслідки:**
  * Повна безстатусність (stateless) API-серверів, що спрощує горизонтальне масштабування (`NFR-08`).
  * Готова підтримка корпоративного SSO, 2FA та інтеграції з університетським LDAP/AD через Keycloak.
  * Надійний захист від підробки токенів (асиметричний підпис `RS256`) та перехоплення токенів через XSS (завдяки `HttpOnly` cookies для Refresh Token).
* **Негативні наслідки / Компроміси (Trade-offs):**
  * Неможливість миттєво анулювати вже виданий `Access Token` до завершення його 15-хвилинного вікна життя без використання чорного списку (Blacklist у Redis) для критичних випадків блокування акаунта.
  * Додаткові витрати оперативної пам'яті (~512 МБ–1 ГБ RAM) на розгортання та резервне копіювання екземпляра Keycloak.
